# 邯郸市城市更新项目库系统建模文档

> **建模方法论**：运营本体建模（Ontology-Driven Design）  
> **建模日期**：2026-08-12  
> **适用领域**：城市更新项目库管理  
> **制度依据**：《邯郸市城市更新条例》（2026-07-01 施行）、《河北省城市更新资源数据成果汇交要求》

---

## 一、业务背景与制度闭环

### 1.1 业务目标

邯郸市城市更新项目库系统需要实现从**体检发现问题**到**项目立项**到**年度计划**到**实施评估**的全生命周期管理，形成"发现问题→解决问题→评估成效→复检销号"的闭环。

### 1.2 制度闭环

```
城市体检 → 专项规划 → 片区策划 → 项目库 → 年度计划 → 实施 → 评估 → 复检
   ↑                                                              ↓
   └──────────────────── 问题销号 ←────────────────────────────────┘
```

### 1.3 核心业务流

| 阶段 | 核心动作 | 责任主体 | 产出物 |
|------|---------|---------|--------|
| 体检评估 | 发现问题、分级评估 | 体检部门 | 问题清单、分级报告 |
| 专项规划 | 划定更新区域、明确更新目标 | 规划部门 | 专项规划文本 |
| 片区策划 | 资源调查、策划方案编制 | 片区策划单位 | 片区策划方案 |
| 项目立项 | 项目生成、方案审批 | 住建部门 | 项目库、立项批复 |
| 年度计划 | 项目排期、资金安排 | 领导小组 | 年度实施计划 |
| 项目实施 | 开工建设、进度管理 | 实施单位 | 进度报告、竣工资料 |
| 成效评估 | 评估指标、成效等级 | 体检部门 | 评估报告 |
| 复检销号 | 问题复核、销号归档 | 体检部门 | 销号记录 |

## 二、第一步：对象类型梳理

### 2.1 梳理过程

**核心问题**：业务里有哪些"东西"？

从制度闭环出发，识别出以下实体类别：

1. **资源类**：城市更新的物质载体（地块、建筑、设施、生态、历史文化）
2. **问题类**：体检发现的问题
3. **规划类**：专项规划、片区策划
4. **项目类**：更新项目及其方案
5. **计划类**：年度实施计划
6. **评估类**：实施评估、复检结果
7. **主体类**：参与各方（政府部门、建设单位、设计单位等）
8. **资金类**：资金来源、拨付记录

### 2.2 对象类型清单

| 对象类型 | 说明 | 关键属性 | 可编辑 |
|---------|------|---------|--------|
| **资源地块** | 城市更新资源载体（用地） | 地块编号、资源分类、位置（GIS）、面积、权属、现状用途、建成年份、质量等级 | 部分 |
| **建筑单体** | 城市更新资源载体（建筑） | 建筑编号、所属地块、结构类型、层数、建筑面积、建成年份、质量等级、是否历史建筑 | 部分 |
| **市政设施** | 市政基础设施 | 设施编号、设施类型、位置、建设年份、运行状态、权属单位 | 部分 |
| **公共设施** | 公共服务设施 | 设施编号、设施类型（教育/医疗/文化/体育）、位置、服务能力、权属单位 | 部分 |
| **生态资源** | 生态空间资源 | 资源编号、资源类型（绿地/水系/湿地）、位置、面积、生态等级 | 部分 |
| **历史文化资源** | 历史文化保护对象 | 资源编号、资源类型（历史建筑/街区/文物）、保护等级、位置、面积 | 部分 |
| **体检问题** | 城市体检发现的问题 | 问题编号、问题类型、涉及资源、严重程度、发现年份、问题描述、证据材料 | 部分 |
| **问题分级** | 问题的优先级分级 | 分级编号、关联问题、等级（紧急/重要/一般）、分级依据、分级时间 | 否 |
| **片区** | 片区策划单元 | 片区编号、片区名称、范围（GIS）、面积、策划定位、资源清单、实施时序 | 部分 |
| **更新项目** | 城市更新项目 | 项目编号、项目名称、项目类型、范围（GIS）、投资估算、状态、主管部门、立项时间 | 是（流转） |
| **项目方案** | 项目的实施方案 | 方案编号、关联项目、方案内容、投资明细、实施时序、审批状态 | 部分 |
| **年度计划** | 年度实施计划 | 计划编号、年度、项目清单、资金安排、责任单位、审批状态 | 是 |
| **实施评估** | 项目实施成效评估 | 评估编号、关联项目、评估年度、评估指标、成效等级、评估结论 | 部分 |
| **复检结果** | 问题复检销号 | 复检编号、关联问题、复检时间、复检结论（已解决/未解决）、销号状态 | 否 |
| **参与主体** | 项目参与各方 | 主体编号、主体名称、主体类型（政府/建设/设计/施工/监理）、联系方式 | 是 |
| **资金来源** | 项目资金来源 | 资金编号、关联项目、资金类型（财政/社会资本/贷款）、金额、到位状态 | 部分 |
| **审批记录** | 各类审批的流程记录 | 审批编号、审批类型、关联对象、审批人、审批时间、审批结论、审批意见 | 否 |

### 2.3 🔴 CHECKPOINT 1 确认点

> **确认内容**：向用户展示对象类型清单，确认以下问题：
> 
> 1. **实体覆盖是否完整**：是否遗漏了业务中的关键实体？
>    - 当前清单覆盖了资源、问题、规划、项目、计划、评估、主体、资金八大类
>    - 可能的遗漏：政策法规、标准规范、投诉建议、公众参与记录
> 
> 2. **命名是否符合业务语言**：对象命名是否与邯郸市实际业务术语一致？
>    - 例如："资源地块"是否应该叫"更新地块"？"体检问题"是否应该叫"问题台账"？
> 
> 3. **属性是否够用**：每个对象的关键属性是否能支撑业务需求？
>    - 例如：建筑单体是否需要"是否危房"属性？资源地块是否需要"征收状态"属性？
> 
> 4. **粒度是否合适**：资源分为地块、建筑、设施等六类，是否过细或过粗？
>    - 如果邯郸市资源调查只分三类，可以合并
>    - 如果需要更细（如市政设施分为道路、管网、桥梁），可以拆分

**用户可能的异议及处理方式**：

| 异议 | 处理 |
|------|------|
| "资源分类太细了，我们只分三类" | 合并为：建设用地、建筑、设施三类，生态和历史文化作为属性而非独立对象 |
| "缺少政策法规对象" | 新增"政策法规"对象，与项目形成"依据"链接 |
| "审批记录不需要独立，可以放在各对象的状态字段里" | 保留审批记录作为独立对象，因为审批是跨对象的通用概念，且需要审计追溯 |
| "参与主体太简单，需要区分角色" | 将"主体类型"改为多值属性，或通过"项目-主体-角色"三元关系表达 |

**假设用户确认**：对象清单基本完整，命名符合业务语言，进入第二步。

## 三、第二步：链接类型梳理

### 3.1 梳理过程

**核心问题**：对象之间有哪些"关系"？

从业务流转出发，识别出以下关系类别：

1. **空间关系**：资源在片区内、项目覆盖资源
2. **因果关系**：问题由资源产生、项目解决问题
3. **归属关系**：项目属于片区、项目纳入年度计划
4. **参与关系**：主体参与项目（带角色）
5. **资金关系**：资金来源支持项目
6. **评估关系**：评估针对项目、复检针对问题
7. **审批关系**：审批记录关联对象

### 3.2 链接类型清单

| 链接类型 | 两端对象 | 关系语义（两侧） | 基数 | 说明 |
|---------|---------|----------------|------|------|
| **位于** | 资源地块/建筑/设施 ↔ 片区 | 资源位于片区内 / 片区包含资源 | N:1 | 空间归属关系 |
| **发现问题** | 资源 ↔ 体检问题 | 资源存在问题 / 问题落在资源上 | 1:N | 因果关系 |
| **问题分级** | 体检问题 ↔ 问题分级 | 问题被分级 / 分级针对问题 | 1:1 | 一对一关系 |
| **解决问题** | 体检问题 ↔ 更新项目 | 问题由项目解决 / 项目解决问题 | N:M | 多对多关系 |
| **覆盖资源** | 更新项目 ↔ 资源 | 项目覆盖资源 / 资源被项目覆盖 | 1:N | 空间关系 |
| **归属片区** | 更新项目 ↔ 片区 | 项目在片区内 / 片区含项目 | N:1 | 归属关系 |
| **纳入计划** | 更新项目 ↔ 年度计划 | 项目纳入年度计划 / 计划包含项目 | N:1 | 归属关系 |
| **实施方案** | 更新项目 ↔ 项目方案 | 项目有方案 / 方案属于项目 | 1:N | 一对多关系 |
| **参与项目** | 参与主体 ↔ 更新项目 | 主体参与项目（带角色） / 项目有主体参与 | M:N | 多对多，需记录角色 |
| **资金来源** | 资金来源 ↔ 更新项目 | 资金支持项目 / 项目使用资金 | N:1 | 归属关系 |
| **实施评估** | 更新项目 ↔ 实施评估 | 项目被评估 / 评估针对项目 | 1:N | 一对多关系 |
| **复检问题** | 体检问题 ↔ 复检结果 | 问题被复检 / 复检针对问题 | 1:N | 一对多关系 |
| **审批记录** | 审批记录 ↔ 任意对象 | 审批关联对象 / 对象有审批记录 | 1:1 | 通用审批链接 |
| **依据政策** | 更新项目 ↔ 政策法规（待确认） | 项目依据政策 / 政策被项目依据 | N:M | 可选链接 |

### 3.3 🔴 CHECKPOINT 2 确认点

> **确认内容**：向用户展示链接类型清单，确认以下问题：
> 
> 1. **关键业务关系是否遗漏**：
>    - 资源与问题、问题与项目、项目与计划、项目与评估——核心链路是否完整？
>    - 是否有"项目依赖项目"（如基础设施先行）的关系？
>    - 是否有"项目冲突项目"（如资金竞争）的关系？
> 
> 2. **基数是否正确**：
>    - 一个问题可以被多个项目解决吗？（如综合改造项目）
>    - 一个项目可以纳入多个年度计划吗？（通常不会，但需确认）
>    - 一个主体可以参与多个项目吗？（通常是的）
> 
> 3. **有没有织成蜘蛛网**：
>    - 链接数量是否过多？是否有可以合并的链接？
>    - "位于"和"覆盖资源"是否可以统一为"空间关联"？
> 
> 4. **孤立对象检查**：
>    - 所有对象是否都有至少一个链接？
>    - "政策法规"对象（如果存在）是否有链接？

**用户可能的异议及处理方式**：

| 异议 | 处理 |
|------|------|
| "问题与项目应该是1:1，一个问题对应一个项目" | 调整为1:1，但保留扩展为N:M的接口（综合改造项目） |
| "参与主体需要记录角色，不能简单M:N" | 引入中间对象"项目参与"，包含主体、项目、角色三个属性 |
| "缺少项目依赖关系" | 新增"依赖"链接，两端都是更新项目，基数N:M |
| "审批记录不需要链接到所有对象，只链接关键对象" | 限定审批记录只链接：更新项目、项目方案、年度计划 |

**假设用户确认**：链接清单基本完整，基数正确，进入第三步。

## 四、第三步：操作类型梳理

### 4.1 梳理过程

**核心问题**：对象能发生哪些"动作"？

从业务闭环出发，按阶段识别操作：

1. **体检阶段**：问题登记、问题分级、问题复核
2. **策划阶段**：片区划定、资源评估、策划编制
3. **立项阶段**：项目立项、方案审批
4. **计划阶段**：纳入年度计划、计划调整
5. **实施阶段**：开工确认、进度填报、竣工验收
6. **评估阶段**：成效评估、复检销号

### 4.2 操作类型清单

#### 4.2.1 体检阶段操作

| 操作 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|------|------|---------|--------|------|------|
| **问题登记** | 问题描述、位置、涉及资源、证据材料 | 问题唯一性校验（同一资源同一类型不重复） | 创建体检问题对象，状态为"待分级" | 体检部门 | 记录登记人、登记时间 |
| **问题分级** | 问题ID、等级（紧急/重要/一般）、分级依据 | 问题状态为"待分级" | 创建问题分级对象，问题状态更新为"已分级" | 专家/体检部门负责人 | 记录分级人、分级时间、分级理由 |
| **问题复核** | 问题ID、复核结论 | 问题状态为"已分级" | 更新问题状态，如复核不通过则退回重新分级 | 体检部门负责人 | 记录复核人、复核时间、复核意见 |

#### 4.2.2 策划阶段操作

| 操作 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|------|------|---------|--------|------|------|
| **片区划定** | 片区名称、范围（GIS）、资源清单 | 范围不与已有片区重叠 | 创建片区对象，关联资源 | 规划部门 | 记录划定人、划定时间 |
| **资源评估** | 资源ID、评估结论、更新建议 | 资源已关联片区 | 更新资源属性，生成评估报告 | 规划部门/专家 | 记录评估人、评估时间 |
| **策划编制** | 片区ID、策划方案内容 | 片区已划定且资源已评估 | 创建片区策划方案，状态为"待审批" | 片区策划单位 | 记录编制人、编制时间 |

#### 4.2.3 立项阶段操作

| 操作 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|------|------|---------|--------|------|------|
| **项目立项** | 项目名称、类型、范围、投资估算、关联问题、关联片区 | 关联问题已分级且状态为"已分级"；符合专项规划 | 创建更新项目对象，状态为"已立项"；建立问题-项目链接 | 住建部门 | 记录立项人、立项时间、立项依据 |
| **方案审批** | 方案ID、审批结论（通过/退回/修改） | 方案状态为"待审批" | 更新方案状态；如通过则项目状态更新为"方案已批" | 住建部门负责人/领导小组 | 记录审批人、审批时间、审批意见 |

#### 4.2.4 计划阶段操作

| 操作 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|------|------|---------|--------|------|------|
| **纳入年度计划** | 项目ID、年度、资金安排、责任单位 | 项目状态为"方案已批" | 创建年度计划记录，项目状态更新为"已纳入计划" | 领导小组 | 记录纳入人、纳入时间 |
| **计划调整** | 计划ID、调整类型（新增/移除/延期）、调整原因 | 年度计划状态为"已审批" | 更新年度计划内容，记录调整历史 | 领导小组 | 记录调整人、调整时间、调整原因 |

#### 4.2.5 实施阶段操作

| 操作 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|------|------|---------|--------|------|------|
| **开工确认** | 项目ID、开工日期、施工单位 | 项目状态为"已纳入计划" | 项目状态更新为"实施中" | 实施单位/住建部门 | 记录确认人、确认时间 |
| **进度填报** | 项目ID、进度百分比、进度描述、佐证材料 | 项目状态为"实施中" | 更新项目进度，创建进度记录 | 实施单位 | 记录填报人、填报时间 |
| **竣工验收** | 项目ID、竣工日期、验收结论（通过/不通过） | 项目进度为100% | 项目状态更新为"已竣工"或退回"实施中" | 住建部门/验收组 | 记录验收人、验收时间、验收意见 |

#### 4.2.6 评估阶段操作

| 操作 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|------|------|---------|--------|------|------|
| **成效评估** | 项目ID、评估年度、评估指标、成效等级 | 项目状态为"已竣工" | 创建实施评估对象，项目状态更新为"已评估" | 体检部门/第三方评估机构 | 记录评估人、评估时间、评估结论 |
| **复检销号** | 问题ID、复检时间、复检结论（已解决/未解决） | 关联项目状态为"已评估" | 创建复检结果对象；如已解决则问题状态更新为"已销号" | 体检部门 | 记录复检人、复检时间、复检结论 |

### 4.3 🔴 CHECKPOINT 3 确认点

> **确认内容**：向用户展示操作类型清单，确认以下问题：
> 
> 1. **每个业务流转动作是否都有对应操作**：
>    - 体检→策划→立项→计划→实施→评估→销号，每个环节是否覆盖？
>    - 是否有"暂停项目""取消项目""项目合并"等操作遗漏？
> 
> 2. **权限是否合理**：
>    - 体检部门、规划部门、住建部门、领导小组、实施单位——权限划分是否符合邯郸市实际？
>    - 是否需要更细粒度的权限（如科室级、个人级）？
> 
> 3. **验证规则是否完整**：
>    - 每个操作的前置条件是否明确？
>    - 是否有状态机遗漏（如项目状态流转是否完整）？
> 
> 4. **审计是否充分**：
>    - 哪些操作需要留痕？当前审计字段是否够用？
>    - 是否需要记录操作前后的数据快照？

**用户可能的异议及处理方式**：

| 异议 | 处理 |
|------|------|
| "缺少项目暂停/取消操作" | 新增"项目暂停""项目恢复""项目取消"操作，需记录原因 |
| "权限划分太粗，需要到科室级" | 在角色表中增加科室维度，操作权限关联到具体科室 |
| "成效评估需要第三方机构，权限要单独设置" | 新增"第三方评估机构"角色，赋予"成效评估"操作权限 |
| "审计需要记录数据快照" | 在审计字段中增加"操作前数据""操作后数据"两个JSON字段 |

**假设用户确认**：操作清单基本完整，权限合理，进入第四步输出设计产物。

## 六、设计说明与权衡

### 6.1 设计决策说明

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 资源分类粒度 | 六类独立对象 | 符合《河北省城市更新资源数据成果汇交要求》的分类体系，便于后续数据汇交 |
| 问题与项目关系 | N:M 多对多 | 支持综合改造项目解决多个问题，也支持一个问题分阶段由多个项目解决 |
| 审批记录独立建模 | 独立对象 | 审批是跨对象的通用概念，独立建模便于审计追溯和流程分析 |
| 参与主体与项目关系 | M:N + 角色属性 | 一个主体可参与多个项目，一个项目有多个主体，角色通过链接属性表达 |
| 项目状态机 | 8个状态 | 覆盖完整生命周期，支持暂停/恢复/取消等异常场景 |

### 6.2 已知权衡

| 权衡点 | 当前选择 | 潜在问题 | 触发重审条件 |
|--------|---------|---------|-------------|
| 资源分类过细 | 六类独立对象 | 数据量小时维护成本高 | 资源总数 < 1000 时可考虑合并 |
| 审批记录独立 | 独立对象 | 查询时需要关联 | 审批类型 < 5 种时可考虑内嵌 |
| 项目状态复杂 | 8个状态 | 状态流转逻辑复杂 | 如业务简化可合并状态 |

### 6.3 后续扩展建议

1. **政策法规对象**：如需要追溯项目依据的政策法规，可新增"政策法规"对象
2. **公众参与对象**：如需要记录公众意见、听证会记录，可新增相关对象
3. **绩效考核对象**：如需要对部门/个人进行绩效考核，可新增绩效指标对象
4. **GIS集成**：所有带位置属性的对象需要与GIS系统集成，支持空间查询和可视化
