# 临漳县低空智能监管平台 - 业务模型设计文档

> **文档版本**：v1.0  
> **适用场景**：自然资源低空监管、土地违法监测、耕地保护、批后监管  
> **建模方法论**：运营本体建模（Ontology-Driven Design）  
> **建模日期**：2026-02-11

---

## 一、建模说明

### 1.1 建模方法论

本文档采用**运营本体建模（Ontology-Driven Design）**方法论，源自 Palantir Foundry Ontology 工程实践。核心思想是回答四个问题：

1. **有什么**（名词）→ 对象类型 Object Type
2. **谁和谁有关**（关系）→ 链接类型 Link Type
3. **能做什么**（动词）→ 操作类型 Action Type
4. **谁能做**（治理）→ 角色 + 权限 + 审计

**关键洞察**：传统数据建模（ER 图、UML）是"只读"的——描述数据是什么，但不描述能对数据做什么。**运营本体把操作、权限、业务规则也编码进模型里**，这是它和生产系统的关键区别。

> 本体的真正价值在"动词"不在"名词"。只建对象+关系不产生运营价值，把操作、权限、回写一起建模进去，模型才能从"摆设"变成"生产力"。

### 1.2 领域核心认知

临漳县自然资源低空智能监管体系不是"把无人机放到地图上"，而是**"时空数据底座 + 套合监管系统 + 卫星遥感 + 低空巡查 + 业务闭环"**的县域自然资源监管体系。

监管真正要回答的问题：
- 变化发生在哪里？占了什么地类？
- 是否压占永久基本农田、生态保护红线、城镇开发边界？
- 是否有审批、是否超审批、是否少批多占？
- 责任主体是谁，归哪个乡镇、村、宗地或权利人？
- 后续如何核查、整改、复核、归档？

> **关键论断**：空间套合比 AI 模型更重要。AI 只做"辅助发现线索"，属性研判靠套合监管。

### 1.3 反模式规避说明

本文档在建模过程中严格规避以下反模式：

| # | 反模式 | 规避措施 |
|---|--------|---------|
| 1 | ❌ 把数据库表 1:1 镜像成对象 | ✅ 采用领域驱动建模：先定义业务概念（设备、任务、图斑、问题），再映射数据源 |
| 2 | ❌ 只建对象和关系，不建模操作 | ✅ 每个业务动作都有操作类型（参数/验证/副作用/权限/审计） |
| 3 | ❌ 用字段名当对象名 | ✅ 用人话命名：`lastInspectionDate` 而非 `dtLastInspMod` |
| 4 | ❌ 织蜘蛛网式链接 | ✅ 链接有业务语义；孤立对象标记"待确认关系" |
| 5 | ❌ 承诺"AI 自动判定违法/问题" | ✅ 明确表达边界："AI 辅助发现线索，属性研判靠人工/套合" |
| 6 | ❌ 做"完美模型"而不产出 | ✅ 先产出能用的版本，标注权衡，逐步迭代 |
| 7 | ❌ 深层单继承链 | ✅ 用接口/抽象（Inspectable、Schedulable）组合 |
| 8 | ❌ 让 AI 自行决定权限 | ✅ 权限矩阵逐项确认，不猜测 |

## 二、对象类型（Object Types）

### 🔴 CHECKPOINT 1：对象类型确认

> **请确认以下对象类型清单**：
> - 实体覆盖是否完整？（设备、任务、成果、图斑、问题、地块）
> - 命名是否符合业务语言？（用"图斑"而非"change_detection_result"）
> - 关键属性是否准确？（主键、业务字段、衍生字段）
> 
> **如有异议，请在此处标注，修订后再进入第二步。**

### 2.1 对象类型清单

| 对象类型 | 说明 | 关键属性 | 可编辑 | 数据来源 |
|---------|------|---------|--------|---------|
| **设备（无人机）** | 一机一档、一机一码的监管设备 | 设备编号（主键）、外部ID映射（民航登记/厂商序列号/公安备案号）、设备类型、在线状态、所属单位、最后维保时间 | 否（来源系统） | 设备管理系统 |
| **任务** | 巡查/核查任务 | 任务编号（主键）、任务类型（巡查/核查/复核）、执行设备、航线、计划时间、实际时间、状态（待执行/进行中/已完成/已取消）、执行人 | 部分（执行状态） | 任务调度系统 |
| **成果资产** | 照片/视频/航迹/识别结果 | 成果编号（主键）、关联任务、关联设备、采集时间、坐标范围、文件类型、存储路径、AI识别结果（辅助） | 否 | 成果管理系统 |
| **图斑/线索** | 变化发现的疑似问题区域 | 图斑编号（主键）、位置（几何）、地类、面积、影像证据、AI置信度（辅助）、发现时间、来源（卫星/低空/举报） | 部分 | 变化检测系统 |
| **问题台账** | 认定后的监管问题 | 问题编号（主键）、问题类型（违法用地/违建/占耕等）、涉及图斑、责任主体、所属乡镇/村、状态（待派发/已派发/整改中/待复核/已销号）、创建时间、处置时限 | 是（流转） | 问题管理系统 |
| **地块/宗地** | 权属单元 | 宗地号（主键）、行政区、村界、权利人、地类、面积、权属性质 | 否 | 权属数据库 |
| **管理数据（套合用）** | 用于属性研判的监管数据 | 地类图斑、永久基本农田、国土空间规划、城镇开发边界、生态保护红线、审批红线、权属/宗地 | 否 | 自然资源一张图 |

### 2.2 设备编码原则

平台主编号只标识设备身份，**不承载**单位、任务、乡镇或临时载荷；外部 ID 作为映射字段维护：

```text
HD-UAV-{区县行政区划代码}-{飞行器类别码}-{四位流水号}
```

示例：`HD-UAV-130425-M-0001`（邯郸市临漳县，多旋翼，0001号）

## 三、链接类型（Link Types）

### 🔴 CHECKPOINT 2：链接类型确认

> **请确认以下链接类型清单**：
> - 有没有漏掉关键业务关系？（执行、产出、发现、认定、归属、套合）
> - 有没有织成蜘蛛网？（每个链接都有明确业务语义）
> - 基数是否正确？（1:1 / 1:N / M:N）
> 
> **如有异议，请在此处标注，修订后再进入第三步。**

### 3.1 链接类型清单

| 链接类型 | 两端对象 | 关系语义（正向 / 反向） | 基数 | 业务说明 |
|---------|---------|----------------------|------|---------|
| **执行** | 任务 ↔ 设备 | 任务使用设备 / 设备执行任务 | N:1 | 一个任务使用一台设备，一台设备可执行多个任务 |
| **产出** | 任务 ↔ 成果资产 | 任务产出成果 / 成果来自任务 | 1:N | 一个任务产出多个成果（照片/视频/航迹） |
| **发现** | 成果资产 ↔ 图斑/线索 | 成果包含图斑 / 图斑来自成果 | 1:N | 一个成果可发现多个图斑（变化检测） |
| **认定** | 图斑/线索 ↔ 问题台账 | 图斑转为问题 / 问题源于图斑 | N:1 | 多个图斑可合并为一个问题，或一个图斑认定为一个问题 |
| **归属** | 问题台账 ↔ 地块/宗地 | 问题位于地块 / 地块存在问题 | N:1 | 一个问题可能涉及多个地块，一个地块可能有多个问题 |
| **套合** | 图斑/线索 ↔ 管理数据 | 图斑套合判断属性 / 管理数据被图斑套合 | M:N | 图斑与地类/规划/红线/审批/权属套合，判断属性 |
| **派发** | 问题台账 ↔ 处置单位 | 问题派发给单位 / 单位处置问题 | 1:1 | 一个问题派发给一个处置单位 |
| **整改** | 问题台账 ↔ 整改记录 | 问题需要整改 / 整改记录对应问题 | 1:N | 一个问题可能有多次整改记录（退回重改） |
| **复核** | 问题台账 ↔ 复核记录 | 问题需要复核 / 复核记录对应问题 | 1:N | 一个问题可能有多次复核记录（复核不通过） |

### 3.2 套合对象表（判断用）

| 套合对象 | 套合目的 | 输出判断 |
|---------|---------|---------|
| 地类图斑 | 判断占用地类 | 耕地/建设用地/林地/园地/未利用地 |
| 永久基本农田 | 判断是否触碰底线 | 是否占用永久基本农田 |
| 国土空间规划 | 判断是否符合规划用途 | 是否符合规划管控要求 |
| 城镇开发边界 | 判断建设管控范围 | 集中建设区/边界外 |
| 生态保护红线 | 判断生态约束 | 是否压占生态保护红线 |
| 审批红线 | 判断合法审批依据 | 未批先建/超范围/少批多占 |
| 权属/宗地 | 判断责任主体 | 关联乡镇/村/单位/权利人 |

## 四、操作类型（Action Types）

### 🔴 CHECKPOINT 3：操作类型确认

> **请确认以下操作类型清单**：
> - 每个业务流转动作是否都有对应操作？（派发、认领、整改上报、复核、销号归档）
> - 权限是否合理？（监管中心、处置单位、处置人）
> - 审计字段是否完整？（谁、何时、基于什么数据、做了什么决定）
> 
> **如有异议，请在此处标注，修订后再进入第四步。**

### 4.1 操作类型清单

| 操作类型 | 参数 | 验证规则 | 副作用 | 权限 | 审计 |
|---------|------|---------|--------|------|------|
| **派发** | 问题ID、处置单位、处置时限 | 问题已认定且未派发 | 创建整改任务、通知处置单位、问题状态→已派发 | 监管中心 | 记录派发人、派发时间、处置单位、时限 |
| **认领** | 任务ID、处置人 | 任务已派发且未认领 | 任务状态→进行中、通知监管中心 | 处置单位 | 记录认领人、认领时间 |
| **整改上报** | 任务ID、整改照片、整改说明、整改完成时间 | 有整改动作（照片+说明） | 问题状态→待复核、通知监管中心 | 处置单位 | 记录上报人、上报时间、整改内容 |
| **复核** | 任务ID、复核影像、复核结论（通过/不通过）、复核说明 | 必须有整改上报记录 | 通过→问题状态→已销号；不通过→问题状态→整改中（退回） | 监管中心 | 记录复核人、复核时间、复核结论、复核说明 |
| **销号归档** | 问题ID | 复核通过 | 问题状态→已归档、生成台账、归档影像证据 | 监管中心 | 记录归档人、归档时间、归档结论 |
| **变更** | 对象ID、变更内容、变更原因 | 权限校验 | 写入变更记录、通知相关方 | 按角色 | 完整变更日志（谁、何时、改了什么、为什么改） |
| **退回** | 问题ID、退回原因 | 问题状态为整改中或待复核 | 问题状态→待派发（重新派发）或整改中（重新整改） | 监管中心 | 记录退回人、退回时间、退回原因 |

## 五、权限矩阵

### 5.1 角色定义

| 角色 | 说明 | 典型用户 |
|------|------|---------|
| **监管中心** | 县级自然资源监管部门，负责问题认定、派发、复核、销号 | 县自然资源局执法人员 |
| **处置单位** | 乡镇政府或相关职能部门，负责问题整改 | 乡镇政府、城管、住建等 |
| **处置人** | 处置单位指定的具体执行人 | 乡镇执法人员、村干部 |
| **系统管理员** | 系统运维人员，负责设备、用户、配置管理 | 信息中心技术人员 |
| **查询用户** | 只读查看权限 | 领导、其他部门人员 |

### 5.2 权限矩阵

| 角色 | 可读对象 | 可编辑对象 | 可执行操作 |
|------|---------|-----------|-----------|
| **监管中心** | 所有对象 | 问题台账、复核记录、归档记录 | 派发、复核、销号归档、退回、变更 |
| **处置单位** | 本单位相关问题、任务 | 整改记录 | 认领、整改上报 |
| **处置人** | 本人负责的问题、任务 | 整改记录 | 认领、整改上报 |
| **系统管理员** | 所有对象 | 设备、用户、配置 | 设备管理、用户管理、系统配置 |
| **查询用户** | 所有对象 | 无 | 无（只读） |

### 5.3 权限控制原则

1. **最小权限原则**：每个角色只拥有完成工作所需的最小权限
2. **职责分离原则**：派发人和处置人不能是同一人；复核人和整改人不能是同一人
3. **审计追溯原则**：所有操作都有审计日志，不可篡改
4. **权限变更审批**：权限变更需要监管中心审批，记录变更日志

## 六、闭环流程（业务流转）

### 6.1 问题闭环主线

```
影像采集 → 智能识别 → 疑似图斑 → 自动套合 → 属性研判 → 人工核查 → 整改处置 → 低空复核 → 台账归档
```

### 6.2 状态流转图

```
┌──────────┐
│ 待派发    │ ← 问题认定后初始状态
└────┬─────┘
     │ 派发
     ▼
┌──────────┐
│ 已派发    │
└────┬─────┘
     │ 认领
     ▼
┌──────────┐
│ 整改中    │ ←──────┐ （复核不通过，退回整改）
└────┬─────┘        │
     │ 整改上报      │
     ▼              │
┌──────────┐        │
│ 待复核    │ ───────┘ （复核不通过）
└────┬─────┘
     │ 复核通过
     ▼
┌──────────┐
│ 已销号    │
└────┬─────┘
     │ 归档
     ▼
┌──────────┐
│ 已归档    │
└──────────┘
```

### 6.3 六条主线（平台建设重点）

| 主线 | 说明 | 优先级 |
|------|------|--------|
| **设备底账** | 一机一档、一机一码，设备全生命周期管理 | 高 |
| **实时态势** | 设备在线状态、任务执行情况、问题分布 | 中 |
| **任务管理** | 任务派发、执行、成果提交 | 高 |
| **成果资产** | 照片/视频/航迹/识别结果的统一管理 | 高 |
| **空间套合** | 图斑与地类/规划/红线/审批/权属套合 | 高 |
| **问题闭环** | 派发→核查→整改→复核→销号归档 | 最高 |

> **关键论断**：缺一不可，只做 AI 识别不做处置闭环是最大坑。

## 八、表达边界（写方案时遵守）

1. **不把低空巡查讲成主角**，主角是自然资源监管体系
2. **不承诺 AI 自动判定违法**，只表达为辅助发现线索和辅助研判属性
3. **场景必须贴合地方实际**（如临漳县没有矿山就不设矿山监管）
4. **不把展示型大屏作为优先建设重点**，设备底账和问题闭环更关键
