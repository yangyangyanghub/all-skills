# 软件开发预算测算（人月法/功能点法）

为软件/信息化项目生成财政评审可用的预算测算表。所有算术由内置脚本完成（零算术误差），所有取值有文件出处（评审可辩护）。

## 三种计费方法（选型）

| 方法 | 公式 | 适用场景 |
|------|------|---------|
| **人月法**（method=personmonth，默认） | 人月 × 人月单价 | 工作量可估（有模块清单/类比项目）；最通用 |
| **功能点→工作量法**（同上，模块给 fp） | FP×复用度×生产率÷176 → 人月 → 费用 | 有功能规模但工作量未知；GB/T 36964 主公式 |
| **功能点单价法**（method=fp_unit） | 调整后FP × 功能点单价 × 规模变更因子 | 评审方要求功能点口径（山东/北京常用）；快速概算 |

三种方法互为交叉验证：同一项目两种方法测算结果差 <20% 属正常；偏差大时在假设节说明原因（通常为功能点计数口径或复用度判断差异）。

## 工作流

### 第 1 步：收集输入（缺什么问什么，一次问完）

必需信息：
1. **项目名称**（用于测算表标题）
2. **项目所在城市**（决定人月费率基准，查 `references/benchmark-csbmk-2025.md` 城市）
3. **建设内容清单**，两种形态任一：
   - 已知功能点：模块名 + 估算功能点数（+ 复用度：高 1/3 / 中 2/3 / 低 1）
   - 已知人月：模块名 + 人月数
4. **口径边界**：是否含运维费/云资源/等保（默认不含，单列提示）

已知信息（如总价 400 万要求分解）则跳过提问，直接进第 2 步反推。

### 第 2 步：确定参数

读 `references/benchmark-csbmk-2025.md` 确认：
- **人月费率 F**：按城市查表（P50）。用户指定单价则用指定值，但须标注与基准的偏差方向（高/低于基准多少）
- **生产率 PDR**：默认电子政务 P50 = 6.41 人时/功能点；非政务项目查对应行业；估算区间可用 P25/P75
- **复用度 RE**：新建默认低（1.0）；基于底座/既有系统开发取中（2/3）；通用模块（用户管理、日志等）取高（1/3）
- **人月折算系数 HM**：176 人时/月（GB/T 36964-2018）

读 `references/policy-files.md` 确认立项程序依据（按项目所在省匹配定价文件；无省级定价文件的省份按"CSBMK 城市基准 + 国标 + 邻省校准"组合，并在测算表中如实说明）。

🔴 **CHECKPOINT（单价偏离确认）**：单价取值高于 CSBMK 城市基准时，暂停——先向用户说明超出幅度与理由，获认可后再继续；低于基准可直接继续，在测算表标注"保守合理"。

### 第 3 步：运行测算脚本（算术一律用脚本，不手算）

写一个输入 JSON（临时文件），运行：

```bash
python <skill目录>/scripts/calc_budget.py <input.json> -o <输出.md>
```

输入 JSON 格式：

```json
{
  "project": "XX市行政审批智能体平台",
  "city": "邯郸",
  "method": "personmonth",
  "rate_mode": "auto",
  "rate_override": null,
  "cf": 1.39,
  "modules": [
    {"name": "智能体运行时", "role": "架构师+后端", "work": "运行时集成、权限门控、事件审计", "personmonths": 10},
    {"name": "预审工作台", "role": "前端+后端", "work": "AI预审意见+人工复核", "fp": 85, "re": "2/3"},
    {"name": "事项智能体开发", "role": "业务分析+开发+测试", "work": "60个事项技能包", "sub_items": [
      {"name": "A类复杂", "count": 15, "fp": 125, "re": "2/3"},
      {"name": "B类中等", "count": 25, "fp": 85, "re": "2/3"}
    ]}
  ],
  "sections_note": "本表仅测算软件开发费；云资源、等保测评、运维费立项时单列"
}
```

- `method`: `"personmonth"` 人月法（默认）/ `"fp_unit"` 功能点单价法
- 模块给 `personmonths`（人月已知）或 `fp`（功能点，配合 `re`）；`sub_items` 用于按档分组的批量事项（count × 单个功能点）
- `rate_mode`: `"auto"` 按城市查 CSBMK 基准；或 `"custom"` 配 `rate_override`（元/人月）
- `cf`: 规模变更因子（fp_unit 模式：概算/预算 1.39、投标/计划 1.21、需求分析 1.10、交付 1.00）
- `pdr` 可选（默认 6.41 电子政务 P50）；`hm` 可选（默认 176）

脚本输出 markdown 测算表（含换算过程列、合计行校验）。

### 第 4 步：组装交付文档

把脚本输出嵌入完整测算表模板（结构如下），补齐脚本不管的部分：

```markdown
# {项目名}软件开发费人月法测算表
> 测算对象 / 测算方法 / 编制日期
## 一、测算口径与总公式        ← 口径边界（软件费/云资源/等保/运维的边界）+ 公式
## 二、人月费用单价取值及依据   ← 城市基准 + 邻省/省份文件对照（读 policy-files.md 生成）
## 三、软件开发费人月明细       ← 【脚本输出】
## 四、功能点换算依据（如有）   ← 【脚本输出含换算列时并入】
## 五、项目团队角色结构        ← 按人月总数按比例拆角色（需求15-20%/开发40-50%/测试10-15%/实施5-10%）
## 六、依据文件清单            ← 【读 policy-files.md 按省份生成】
## 七、假设与待校准项          ← 单价校准提示、功能点估算性质、口径单列项、著作权归属
## 相关链接                   ← 双链到项目相关文档
```

🔴 **STOP 交付门（数量级校验，写完必查）**：①人月 × 单价 = 各行金额；②分板块小计 = 明细和；③总价 = 用户输入口径。任何不一致 → 重跑脚本修正，未通过校验禁止交付；反推分解场景总价偏差 >0.5% 视为不一致。

### 第 5 步：可选转 docx

政务场景交付时，用 pandoc 转 docx 并套政务字体（黑体标题/仿宋正文/宋体表格）：

```bash
pandoc 输入.md -o 输出.docx --from=gfm && python <项目>/scripts/format_gov_docx.py 输出.docx
```

若工作区无该脚本，跳过格式化仅交付 md。

## 关键规则

1. **算术零手算**：所有乘加进脚本；表格数字与脚本输出一致才可交付。
2. **每个数有出处**：费率→CSBMK 表 4.7；生产率→表 4.2；程序依据→policy-files.md；用户自定义值→标注"建议取值，报审前校准"。
3. **保守优先**：取值低于基准时明说"低于基准，保守合理"；高于基准时须给理由（如含实施调研工作量）。
4. **不编基准数据**：城市不在表内时，用同类别城市均值并在假设节注明；绝不虚构数值。
5. **数据时效**：CSBMK 每年更新（版本号 CSBMK-YYYYMM）。若工作区有更新版基准数据文件，以新版为准并更新引用。

## 红线清单（不要做什么）

以下反模式在政务预算场景会直接导致评审被拒或数据失实，任何一条命中即停止输出并纠正：

1. **不虚构基准数值**——城市不在 CSBMK 表内时取同类别均值并注明，绝不编一个"看起来合理"的费率。
2. **不用全行业生产率冒充领域口径**——政务项目必须用电子政务 P50（6.41），引用全行业值（如 6.96/7.09）须声明为旧版或跨行业口径。
3. **不混口径**——运维费、云资源、等保测评费不混入软件开发费；报价区间不混入确定值口径（反之亦然）。
4. **不手算交付**——任何乘加结果未经脚本生成即写入交付文档，视为无效。
5. **不把用户指定单价标成官方基准**——指定值只能标"建议取值"，与 CSBMK 基准的偏差方向必须写明。
6. **不引用过期版本不注明**——CSBMK 逐年更新，引用时必须带版本号（如 CSBMK®-202510）；发现工作区有新版基准文件时以新版为准。
