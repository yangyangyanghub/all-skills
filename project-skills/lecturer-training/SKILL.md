# 讲师训练营课程设计

## Core rule

课程不是把知识搬给学员，而是带学员完成一次可感知的认知改变。讲师不是知识搬运工，而是登山向导：知识是山，课程结构是路线，材料是沿途台阶，互动是确认学员还在路上的信号。

设计任何课程时，先回答「学员从什么旧认知出发，要抵达什么新认知」，再设计场景、挑战、路线、材料和解决方案。不要从概念解释开始堆内容。

## When to use

在以下任务中使用本技能：

- 设计讲师训练、企业内训、知识分享、公开课、微课、课程大纲、教学脚本。
- 用户说「帮我设计一节课」「梳理课程主题」「写讲课稿」「做培训提纲」「提升讲课效果」。
- 已有材料很多，但课程像资料堆砌，需要重构成一条学习路线。
- 需要把抽象概念转成场景挑战、练习、案例、互动问题和可执行方案。
- 需要诊断一节课为什么无聊、松散、听完没行动、没有认知冲击。
- 需要训练讲师的开场、转场、点评、互动、语言势能和「不是……而是……」建模能力。

## When not to use

不要在以下场景直接使用：

- 用户只要普通文案润色、新闻稿、公众号长文，且不涉及课程或教学。
- 用户只要搜集资料、做学术综述、整理百科定义，不需要教学转化。
- 用户要求照搬源材料原文、大段复刻课程文本。
- 用户要求编造真实案例、学员反馈、讲师亲历或数据效果。
- 课程涉及专业合规、安全、医学、法律、财务等高风险建议，但缺少权威来源；此时只能输出课程结构和待核验证据清单。

## Runtime workflow

1. 判断任务类型：新课设计、主题定位、材料筛选、大纲重构、脚本生成、表达优化、课程评审。
2. 收集或确认输入：对象、场景、旧认知、新认知、课程时长、交付形式、素材来源、约束边界。
3. 先建认知地图：定义「起点认知」和「终点认知」，明确学员必须跨过的挑战。
4. 用「场景 + 挑战 + 解决方案」组织课程，不用「概念 + 解释 + 例子」做主结构。
5. 把知识山拆成路线：起点、坡度、关键台阶、风险点、抵达标志。
6. 按任务读取 references，只加载当前需要的文件。
7. 交付前检查：是否有认知改变、是否有具体挑战、材料是否服务台阶、方案是否可执行。

## 复用思维方法库（method-library）

课程设计的不同环节可调用思维方法库 `method-library` 增强：

| 课程环节 | 复用方法 | 用法 |
|---------|---------|------|
| 课程目标定义 | 5W1H | 澄清对象/场景/目的/方式，避免目标模糊 |
| 学员需求洞察 | JTBD | 学员"雇佣"课程完成什么任务，找到真实动机 |
| 课程结构组织 | 金字塔原理 | 结论先行，先给框架再展开内容 |
| 内容分类拆解 | MECE | 知识模块相互独立、完全穷尽 |
| 学员画像/定位 | SWOT | 分析学员背景的优劣势、机会威胁 |

> 调用方式：`use_skill("method-library")` 加载方法模板后，按对应模板组织该环节。课程框架提供教学结构，思维方法库提供需求分析和目标澄清工具，二者叠加使课程从"知识罗列"升级为"认知设计"。

## Task routing table

| 用户任务 | 执行动作 | 默认交付 |
|---|---|---|
| 课程从零设计 | 先做课程定位卡和认知改变图，再出路线大纲 | 课程定位卡 + 认知改变图 + 路线大纲 |
| 已有主题但不聚焦 | 用场景、对象、挑战筛掉泛主题 | 3 个主题候选 + 推荐主题 + 取舍理由 |
| 材料很多不会选 | 按「能否推动认知台阶」筛选材料 | 材料清单：保留、改写、剔除 |
| 大纲松散 | 把目录重排为登山路线 | 路线型课程提纲 |
| 讲稿无聊 | 增加开场挑战、转场、互动、语言势能 | 讲稿改写建议或 3000 字草稿骨架 |
| 课程评审 | 按质量清单逐项诊断 | 问题清单 + 优先修复建议 |
| 训练讲师表达 | 生成开场、转场、点评、提问语句 | 讲师台词包 |

## Input requirements

尽量从用户输入中提取；缺失时不要编造。

| 信息 | 为什么需要 | 缺失时处理 |
|---|---|---|
| 学员对象 | 决定旧认知、语言和案例 | 先列 2-3 种可能对象让用户选择 |
| 真实场景 | 决定挑战是否成立 | 用「假设场景」标明，不写成事实 |
| 课程目标 | 决定认知终点 | 改写为「听完后能判断/能做什么」 |
| 课程时长 | 决定路线长度和材料密度 | 给 30/60/120 分钟三档结构 |
| 可用材料 | 决定案例和练习来源 | 只用已给材料；缺口列为需补证据 |
| 输出形式 | 决定大纲、讲稿、卡片或评审表 | 默认输出 Markdown 结构化文档 |

## Quality checklist

交付前逐项自检：

- [ ] 是否明确「旧认知 → 新认知」？
- [ ] 是否把讲师定位为向导，而不是知识搬运工？
- [ ] 课程主结构是否来自「场景 + 挑战 + 解决方案」？
- [ ] 是否避免用「概念 + 解释 + 例子」堆目录？
- [ ] 每个材料是否是认知台阶，而不是装饰性故事？
- [ ] 解决方案是否具体到排序、拼图、递进、人物角色等方法？
- [ ] 是否使用「不是……而是……」拆开旧认知和新认知？
- [ ] 大纲是否有路线感：起点、坡度、关键台阶、抵达标志？
- [ ] 互动问题是否帮助学员暴露判断，而不是活跃气氛而已？
- [ ] 没有编造源材料中未提供的原话、案例和数据？

## Red flags / Do not do

- 不要把课程写成资料汇编。
- 不要一上来解释概念、罗列定义、堆知识点。
- 不要把「讲清楚」当成课程目标；目标必须落到认知改变或行动能力。
- 不要使用源材料中没有给出的精确引语。
- 不要复制大段源文，只提炼方法框架。
- 不要用泛泛的「提高认知」「激发兴趣」「赋能成长」替代具体终点。
- 不要把互动设计成寒暄、投票、破冰游戏，除非它服务认知挑战。
- 不要在缺少对象、场景、目标时直接生成完整课程；先标注假设或追问。

## Information gaps handling

当关键信息不足时，按以下顺序处理：

1. 先从用户材料中提取已有事实，不补编。
2. 将缺口分成三类：必须确认、可合理假设、可暂时跳过。
3. 对必须确认的信息，只问最少问题：学员是谁、课后要改变什么、课程时长是多少。
4. 用户不方便补充时，输出「基于假设的版本」，并在开头列明假设。
5. 高风险、强事实、真实案例和效果数据一律标为「需用户提供来源」，不能伪装成已验证事实。
